Algorithms

UnitCellMC.MetropolisAlgorithm — Type
MetropolisAlgorithm(proposal = RandomProposal())

The Metropolis-Hastings single-site update algorithm: a trial move is generated with propose and accepted unconditionally when it lowers the energy, or with probability exp(-ΔE / T) otherwise (see step!).

Fields

  • proposal::AbstractProposalScheme: Which site each update visits — RandomProposal (the default), SequentialProposal, CheckerboardProposal, or ColoredProposal. The model's propose method decides the new value at that site.
source
UnitCellMC.MetropolisUpdateResult — Type
MetropolisUpdateResult

Result of one Metropolis update, recording whether the proposed move was accepted.

Fields

  • accepted::Bool: Whether the proposed update was applied to the state.
source
UnitCellMC.GlauberAlgorithm — Type
GlauberAlgorithm(proposal = RandomProposal())

The Glauber single-site update algorithm: the same trial moves as MetropolisAlgorithm, but a trial move is accepted with probability 1 / (1 + exp(ΔE / T)) instead of the Metropolis min(1, exp(-ΔE / T)).

By default every model proposes the same symmetric single-site trial moves as for MetropolisAlgorithm — a generic fallback propose method forwards to it — so detailed balance holds with respect to the Boltzmann distribution. A model may override the fallback with a Glauber-specific proposal.

Fields

  • proposal::AbstractProposalScheme: Which site each update visits — RandomProposal (the default), SequentialProposal, CheckerboardProposal, or ColoredProposal.

UnitCellMC.glauber_probability — Function
glauber_probability(ΔE, T)

Return the Glauber acceptance probability 1 / (1 + exp(ΔE / T)) for a move with energy change ΔE at temperature T.

The logistic form is evaluated so that it neither overflows nor loses precision: for ΔE > 0 it is rewritten as exp(-ΔE / T) / (1 + exp(-ΔE / T)), which tends to 0 instead of evaluating exp of a large argument.

Returns

A probability in [0, 1].

source
UnitCellMC.WolffAlgorithm — Type
WolffAlgorithm

Marker type selecting a single-cluster Wolff update. The cluster traversal is model-independent; models provide cluster_seed, cluster_bond_probability, and apply_cluster! methods.

With an external field, clusters that attach to a ghost site are never flipped, and for β|h| ≳ 1 most clusters attach — acceptance collapses and the cluster sizes stay small (the WolffUpdateResult cluster_size reports zero for those frozen steps). Prefer a local-update algorithm (MetropolisAlgorithm, GlauberAlgorithm) in strong fields.

source
UnitCellMC.WolffUpdateResult — Type
WolffUpdateResult

Result of one Wolff update, recording the number of sites in the flipped cluster — zero when the grown cluster attached to a ghost site and was therefore not flipped (ghost-attached clusters are never flipped; see step!).

source
UnitCellMC.SwendsenWangAlgorithm — Type
SwendsenWangAlgorithm

Marker type selecting a Swendsen-Wang cluster update. Bond activation is delegated to cluster_bond_probability, and model-specific cluster mutations are delegated to apply_clusters!.

With an external field, clusters that attach to a ghost site are never flipped, and for β|h| ≳ 1 most of the lattice attaches — most steps leave the state unchanged. Prefer a local-update algorithm (MetropolisAlgorithm, GlauberAlgorithm) in strong fields.

source
UnitCellMC.SwendsenWangUpdateResult — Type
SwendsenWangUpdateResult

Result of one Swendsen-Wang update, recording the number of clusters, the total number of lattice sites processed (updated_sites; always equal to geometry.n_sites, since every site belongs to exactly one cluster), and the fraction of sites contained in the largest cluster. The size distribution includes ghost-attached clusters, which are never flipped — with an external field, largest_cluster_fraction can be large even when little changed (see SwendsenWangAlgorithm).

UnitCellMC.step! — Function
step!(alg, model, geometry, state, T; rng = Random.default_rng())

Attempt one Monte Carlo update on state using alg, and apply it if accepted according to the Metropolis criterion at temperature T.

A trial move is generated with propose, its energy change is computed with energy_difference, and it is accepted unconditionally if ΔE <= 0, or with probability exp(-ΔE / T) otherwise. Accepted moves are applied in place via apply_update!.

When workspace carries an AcceptanceCache — the case for models with a discrete ΔE spectrum, see tabulate_acceptance — the Boltzmann factor is memoized per temperature and the test reads rand(rng) < exp(-ΔE / T) with the memoized factor. That is mathematically identical to the uncached log(rand(rng)) < -ΔE / T comparison, but borderline accept/reject decisions can differ in the last floating-point bit.

Arguments

  • alg: The update algorithm to use (e.g. MetropolisAlgorithm()).
  • model: The model defining couplings/energetics.
  • geometry: The lattice geometry.
  • state: The current configuration, mutated in place if the move is accepted.
  • T: Temperature used in the Metropolis acceptance probability.
  • rng: Random number generator used for the proposal and the acceptance test. Defaults to the task-local global RNG, so Random.seed! makes runs reproducible; pass an explicit AbstractRNG for an independent stream.
  • workspace: Per-run scratch space from algorithm_workspace, threaded through MC_Sweep! by the drivers. Required when alg uses a stateful proposal scheme (see SequentialProposal).

Throws

ArgumentError if T is not strictly positive, or if alg uses a stateful proposal scheme and no workspace is given.

Returns

A MetropolisUpdateResult describing whether the proposal was accepted.

source
step!(alg::GlauberAlgorithm, model, geometry, state, T; rng = Random.default_rng())

Attempt one Glauber update on state at temperature T, and apply it if accepted.

A trial move is generated with propose, its energy change is computed with energy_difference, and it is accepted with the Glauber probability 1 / (1 + exp(ΔE / T)). Unlike Metropolis, moves with ΔE <= 0 are not accepted unconditionally; a move with ΔE = 0 is accepted with probability 1/2. Accepted moves are applied in place via apply_update!.

When workspace carries an AcceptanceCache — the case for models with a discrete ΔE spectrum, see tabulate_acceptance — the Boltzmann factor u = exp(-ΔE / T) is memoized per temperature and the probability evaluated as u / (1 + u) for ΔE > 0 and 1 / (1 + 1 / u) otherwise, which matches glauber_probability up to the last floating-point bit.

Arguments

  • alg: The update algorithm, GlauberAlgorithm().
  • model: The model defining couplings/energetics.
  • geometry: The lattice geometry.
  • state: The current configuration, mutated in place if the move is accepted.
  • T: Temperature used in the Glauber acceptance probability.
  • rng: Random number generator used for the proposal and the acceptance test. Defaults to the task-local global RNG, so Random.seed! makes runs reproducible; pass an explicit AbstractRNG for an independent stream.
  • workspace: Per-run scratch space from algorithm_workspace, threaded through MC_Sweep! by the drivers. Required when alg uses a stateful proposal scheme (see SequentialProposal).

Throws

ArgumentError if T is not strictly positive, or if alg uses a stateful proposal scheme and no workspace is given.

Returns

A GlauberUpdateResult describing whether the proposal was accepted.

source
step!(WolffAlgorithm(), model, geometry, state, T;
    rng = Random.default_rng(), workspace = nothing)

Grow and flip one Wolff cluster. Model-specific behavior is supplied by cluster_bond_probability and apply_cluster!, which keeps the cluster traversal reusable for models with different local degrees of freedom. All random numbers (cluster context, seed site, bond activation) come from rng.

Growth stops as soon as the cluster attaches to a ghost site (see ghost_site): ghost-attached clusters are never flipped, so growing further would be wasted work.

The cluster mask and member/frontier lists are taken from workspace (a ClusterWorkspace) when given and allocated fresh otherwise; drivers allocate one workspace per run via algorithm_workspace.

source
step!(SwendsenWangAlgorithm(), model, geometry, state, T;
    rng = Random.default_rng(), workspace = nothing)

Activate each undirected bond once, form connected components with union-find, and pass the completed clusters to apply_clusters!. The bond traversal is model-independent and the model controls both bond activation and mutation. All random numbers (cluster context, bond activation, cluster flips) are drawn from rng.

Clusters are labelled by union-find root id: after the bond pass, workspace.labels[i] is the label of site (or ghost) i and workspace.roots lists the labels that contain at least one lattice site. The union-find arrays and label buffers come from workspace (a ClusterWorkspace) when given and are allocated fresh otherwise; drivers allocate one workspace per run via algorithm_workspace.

source
UnitCellMC.steps_per_sweep — Function
steps_per_sweep(algorithm, geometry)

Return the number of step! updates that constitute one Monte Carlo sweep for algorithm on geometry.

For local-update algorithms (the default, e.g. MetropolisAlgorithm and GlauberAlgorithm) a sweep is geometry.n_sites single-site updates, so that on average every site is updated once per sweep — exactly once with SequentialProposal, which visits the sites in order. For cluster algorithms (WolffAlgorithm, SwendsenWangAlgorithm) a single cluster update already moves a macroscopic fraction of the lattice, so a sweep is exactly one call to step!.

Extend this function to change the sweep size for a custom algorithm.

source
UnitCellMC.AbstractProposalScheme — Type
AbstractProposalScheme

Abstract supertype for the site-selection schemes of local-update algorithms (MetropolisAlgorithm, GlauberAlgorithm).

A scheme decides which site each step! update visits — RandomProposal draws uniformly at random, SequentialProposal cycles through the lattice in site-index order, CheckerboardProposal and ColoredProposal sweep one color class of sites and then the next — while the model's propose method decides the new value at that site. Stateful schemes carry their per-run state in a workspace built by proposal_workspace, which the drivers thread into step!.

source
UnitCellMC.RandomProposal — Type
RandomProposal

Site-selection scheme for local-update algorithms (MetropolisAlgorithm, GlauberAlgorithm): every step! update draws a site uniformly at random from rng. This is the default scheme.

source
UnitCellMC.SequentialProposal — Type
SequentialProposal

Site-selection scheme for local-update algorithms (MetropolisAlgorithm, GlauberAlgorithm): step! updates visit the sites in site-index order, so one sweep (steps_per_sweep updates) attempts every site exactly once instead of n_sites random draws.

LatticeUtilities.jl numbers sites in column-major unit-cell order (the first lattice direction varies fastest), so consecutive updates target neighboring sites — on a square lattice the sweep proceeds column by column (equivalently row by row, up to transposition).

Each single-site update still satisfies detailed balance, so the completed sweep leaves the Boltzmann distribution invariant; only the visiting order differs from RandomProposal.

The cursor is mutable per-run state held in a SequentialProposalWorkspace, built once per run by algorithm_workspace and threaded into step! by the drivers. Calling step! or propose directly without a workspace throws an ArgumentError, since a fresh cursor would restart at site 1 on every call.

source
UnitCellMC.SequentialProposalWorkspace — Type
SequentialProposalWorkspace

Per-run cursor for the SequentialProposal scheme: next is the site the next step! update visits. Built by proposal_workspace via algorithm_workspace. Like ClusterWorkspace, it carries mutable state between steps and must not be shared between concurrent runs.

source
UnitCellMC.CheckerboardProposal — Type
CheckerboardProposal

Site-selection scheme for local-update algorithms (MetropolisAlgorithm, GlauberAlgorithm) on bipartite lattices: the sites are 2-colored so that no bond connects same-color sites (see checkerboard_colors), and each sweep first updates all sites of one color, then all sites of the other. Within a color, sites are visited in site-index order. For lattices that need more than two colors see ColoredProposal.

Same-color sites share no bond, so the updates within each half-sweep do not interact directly — on a square lattice this is the classic checkerboard decomposition, where one color holds the even-parity sites mod(x + y, 2) == 0 and the other the odd-parity ones. Each single-site update still satisfies detailed balance, so the completed sweep leaves the Boltzmann distribution invariant.

The visiting order and cursor are per-run state held in a ColoredProposalWorkspace, built once per run by algorithm_workspace and threaded into step! by the drivers. Calling step! or propose directly without a workspace throws an ArgumentError, as does any non-bipartite lattice (e.g. triangular) when the workspace is built.

source
UnitCellMC.ColoredProposal — Type
ColoredProposal(k)

Site-selection scheme for local-update algorithms (MetropolisAlgorithm, GlauberAlgorithm): the sites are colored with at most k colors so that no bond connects same-color sites (see color_lattice), and each sweep updates all sites of one color class, then the next — e.g. ColoredProposal(3) for the tripartite triangular or kagome lattices. Within a color class, sites are visited in site-index order.

Same-color sites share no bond, so the updates within each color block do not interact directly, and each single-site update satisfies detailed balance, so the completed sweep leaves the Boltzmann distribution invariant.

The coloring is a saturation-first greedy (DSATUR) with randomized restarts; see color_lattice. Exact coloring is NP-hard in general, so if no attempt manages with k colors an ArgumentError is thrown when the workspace is built — even where a k-coloring exists. DSATUR is exact on bipartite graphs, but for k = 2 prefer CheckerboardProposal, whose coloring is cheaper and needs no restarts.

The visiting order and cursor are per-run state held in a ColoredProposalWorkspace, built once per run by algorithm_workspace and threaded into step! by the drivers. Calling step! or propose directly without a workspace throws an ArgumentError.

Throws

ArgumentError if k < 2.

source
UnitCellMC.ColoredProposalWorkspace — Type
ColoredProposalWorkspace

Per-run state for the CheckerboardProposal and ColoredProposal schemes. Built by proposal_workspace via algorithm_workspace. Like ClusterWorkspace, it carries mutable state between steps and must not be shared between concurrent runs.

Fields

  • order::Vector{Int}: The visiting order — each color class in turn, in site-index order within a class (see checkerboard_colors and color_lattice).
  • next::Int: Cursor into order; the next step! update visits order[next].

UnitCellMC.checkerboard_colors — Function
checkerboard_colors(geometry)

2-color the bond graph of geometry: return a Vector{Int} with one entry per site, 0 or 1, such that the two endpoints of every bond have opposite colors. On a square lattice this is the parity mod(x + y, 2) of the unit cell coordinates. The neighbor table lists each bond from both endpoints, so every bond constrains the coloring exactly once per direction.

Throws

ArgumentError if the bond graph is not bipartite — a bond whose endpoints the coloring forces to equal colors (e.g. the triangles of a triangular lattice), or a bond from a site to itself.

source
UnitCellMC.color_lattice — Function
color_lattice(geometry, k)

Color the bond graph of geometry with at most k colors: return a Vector{Int} with one entry per site in 1:k such that the two endpoints of every bond have different colors.

The coloring is a saturation-first greedy (DSATUR): each step colors the uncolored site adjacent to the most distinct colors, breaking ties by degree. Fewer than k colors may be used. DSATUR is exact on bipartite graphs and handles the usual regular lattices (e.g. the tripartite triangular and kagome lattices with k = 3), but exact coloring is NP-hard in general. The first pass is the classical deterministic algorithm (ties by degree, then site index; smallest available color); if a site gets stuck, up to 15 further passes randomize both the tie-breaking and the choice among available colors. The restarts draw from a fixed internal random stream, so the resulting coloring is identical between runs and independent of the simulation rng. Even so, success is not guaranteed where a k-coloring exists; for k = 2 use checkerboard_colors, which is cheaper and needs no restarts.

Throws

ArgumentError if k < 2, if a site is bonded to itself, or if no attempt manages with k colors.

source
UnitCellMC.propose_site — Function
propose_site(rng, scheme, geometry, workspace)

Return the site the next local step! update visits under scheme. RandomProposal draws uniformly from rng and ignores workspace; SequentialProposal, CheckerboardProposal, and ColoredProposal return the cursor of their workspace and advance it, wrapping after geometry.n_sites.

UnitCellMC.proposal_workspace — Function
proposal_workspace(scheme, geometry, order = nothing)

Return the per-run site-selection state for scheme: nothing for stateless schemes (RandomProposal), a SequentialProposalWorkspace for SequentialProposal, a ColoredProposalWorkspace for CheckerboardProposal and ColoredProposal. algorithm_workspace bundles the result with the model's AcceptanceCache in a LocalUpdateWorkspace for local-update algorithms, and run_simulation threads it through MC_Sweep! into step!. Extend it for custom schemes with per-run state.

For the colored schemes, order reuses a precomputed visiting_order instead of re-coloring geometry; it must be exactly visiting_order(scheme, geometry) (the coloring is deterministic) — sweep_Ts shares one coloring across its runs this way. nothing (the default, and the only value stateless schemes accept) recomputes it. An order a scheme has no specific three-argument method for is discarded and the workspace rebuilt, so a custom scheme that exposes visiting_order keeps working without one — define the three-argument method to actually receive the shared order.

Throws

ArgumentError from CheckerboardProposal if geometry is not bipartite (see checkerboard_colors), or from ColoredProposal if color_lattice cannot color it with the requested number of colors; also if order is not a permutation of 1:geometry.n_sites.

source
UnitCellMC.visiting_order — Function
visiting_order(scheme, geometry)

Return the deterministic, geometry-only site-visiting order of a colored proposal scheme — the same order vector every ColoredProposalWorkspace would carry for geometry — or nothing for schemes without one (RandomProposal, SequentialProposal).

The order depends only on the scheme and the geometry, so drivers simulating the same geometry many times (sweep_Ts) build it once and share it across runs via proposal_workspace(scheme, geometry, order); only the cursor is per-run state.

Throws

ArgumentError from checkerboard_colors or color_lattice if the geometry cannot be colored as the scheme requires.

source
UnitCellMC.LocalUpdateWorkspace — Type
LocalUpdateWorkspace

Per-run workspace for the local-update algorithms (MetropolisAlgorithm, GlauberAlgorithm), built by algorithm_workspace and threaded through MC_Sweep! into step!. Bundles the site-selection scheme's per-run state with the acceptance-probability memo table.

Fields

  • proposal: The AbstractProposalScheme's per-run state — nothing for RandomProposal, a SequentialProposalWorkspace or ColoredProposalWorkspace for the stateful schemes.
  • acceptance: An AcceptanceCache when tabulate_acceptance is true for the model, nothing otherwise.

Like ClusterWorkspace, it carries mutable state between steps and must not be shared between concurrent runs.

source
UnitCellMC.AcceptanceCache — Type
AcceptanceCache

Per-run memo table of Boltzmann factors u = exp(-ΔE / T) for the local-update acceptance tests, built by algorithm_workspace as part of a LocalUpdateWorkspace when tabulate_acceptance is true for the model. The Metropolis test rand(rng) < exp(-ΔE / T) and the Glauber acceptance probability both become table lookups once an entry is memoized.

Entries are keyed by the exact Float64 value of each computed ΔE, so a hit reproduces a direct exp(-ΔE / T) evaluation bit for bit. The table is cleared when T changes between updates (the drivers use a fixed T per run, so this happens at most once) and holds at most ACCEPTANCE_CACHE_CAPACITY entries; a wider spectrum (say a large-q ClockModel) simply stops memoizing new values once full, while already-memoized values are still served — the commonest ΔEs are met first, so they are the ones retained. Like ClusterWorkspace, it carries mutable per-run state and must not be shared between concurrent runs.

source
UnitCellMC.ACCEPTANCE_CACHE_CAPACITY — Constant
ACCEPTANCE_CACHE_CAPACITY

Maximum number of memoized ΔE → exp(-ΔE / T) entries held by an AcceptanceCache, so the memo table is bounded and its scan stays short. The typical models selected by tabulate_acceptance have far fewer distinct ΔE values than this; a wider spectrum keeps the first entries (the commonest, since they are met first) and computes further values directly.

source
UnitCellMC.tabulate_acceptance — Function
tabulate_acceptance(model)

Return true if the model's single-site energy_difference takes values from a small discrete set, so that local-update algorithms (MetropolisAlgorithm, GlauberAlgorithm) benefit from memoizing Boltzmann factors per temperature in an AcceptanceCache. Memoization is exact whenever the spectrum is discrete, since computed ΔE values repeat bit for bit.

The default is false, appropriate for continuous-spectrum models (XYModel, HeisenbergModel) whose ΔE values essentially never repeat, and for ClockModel, whose spectrum is discrete but grows with q times the coordination number, so beyond small q the scan outweighs the saved exp (measured). Extend it for a custom model with a small discrete spectrum.

source
UnitCellMC.cached_boltzmann_factor — Function
cached_boltzmann_factor(cache, ΔE, T)

Return exp(-ΔE / T), memoized in cache keyed by the exact Float64 value of ΔE (see AcceptanceCache). The first occurrence of each distinct ΔE at temperature T pays for the exp; later occurrences are a short linear scan. Once the cache holds ACCEPTANCE_CACHE_CAPACITY entries, new values are computed directly without being memoized.

source

reset!(cache::AcceptanceCache, T)

UnitCellMC.sweep_steps! — Function
sweep_steps!(algorithm, model, geometry, state, T, stats, diagnostics;
    rng, workspace)

Run the steps_per_sweep step! updates that make up one Monte Carlo sweep of algorithm at temperature T, accumulating the per-update diagnostics selected by diagnostics (a Val wrapping the requested keys, from the MeasurementContainer type parameter) into the UpdateStatistics of stats. Called by MC_Sweep! after it resets stats.

The default method loops over step!, recording diagnostic_values after each update. A model/algorithm pair with a fused fast path — currently single-orbital IsingModel lattices under MetropolisAlgorithm with RandomProposal — may override it, but an override must visit sites and draw from rng exactly as the generic loop does, keep the state's running totals exact, and record identical diagnostics.

UnitCellMC.ClusterWorkspace — Type
ClusterWorkspace

Reusable scratch buffers for the cluster algorithms (WolffAlgorithm and SwendsenWangAlgorithm).

Cluster updates need several lattice-sized arrays per step (cluster masks, member lists, union-find arrays). A ClusterWorkspace is allocated once per run by run_simulation and threaded through MC_Sweep! into step!, so repeated steps reuse the same buffers instead of reallocating them. Calling step! without a workspace allocates one per call.

The buffers are grown lazily on first use and reset at the start of every step. A workspace carries mutable state between steps, so it must not be shared between concurrent runs.

Fields

  • in_cluster::BitVector: Wolff cluster-membership mask.
  • cluster::Vector{Int}: Wolff cluster member list.
  • frontier::Vector{Int}: Wolff breadth-first stack.
  • parents::Vector{Int}: Swendsen-Wang union-find parent of each site, then each ghost site.
  • ranks::Vector{UInt8}: Swendsen-Wang union-find ranks.
  • labels::Vector{Int}: Swendsen-Wang union-find root ("cluster label") of each site, then each ghost site, after the bond-activation pass.
  • roots::Vector{Int}: The distinct labels containing at least one lattice site, in first-encounter order.
  • sizes::Vector{Int}: Per-root lattice-site counts.
  • flip::Vector{Bool}: Per-root cluster orientation decision, drawn by draw_cluster_flips!.
  • seen::BitVector: First-encounter markers used to build roots.
  • validated::Bool: Whether validate_cluster_model has run on this workspace; the model-level check runs once per run (i.e. per workspace), not once per step. A workspace must not be reused with a different model.
source
UnitCellMC.algorithm_workspace — Function
algorithm_workspace(algorithm, model, geometry, state, shared = ...)

Return the per-run scratch space that step! reuses for algorithm: a ClusterWorkspace for cluster algorithms, a LocalUpdateWorkspace for local-update algorithms (MetropolisAlgorithm, GlauberAlgorithm), nothing otherwise. run_simulation allocates it once and passes it through MC_Sweep!. Extend this for custom algorithms with per-step allocations.

The optional shared argument carries shared_workspace(algorithm, model, geometry) — deterministic per-geometry data reused across runs; by default it is recomputed. The five-argument fallback delegates to the four-argument form, so a custom algorithm with an existing four-argument method keeps working (but does not benefit from the sharing). To receive shared, define a single method with a defaulted fifth argument:

algorithm_workspace(alg::MyAlgorithm, model, geometry, state,
                    shared = shared_workspace(alg, model, geometry)) = ...

Do not instead write a four-argument method that delegates to the five-argument form without a five-argument method of your own — that recurses through the fallback forever.

source
UnitCellMC.shared_workspace — Function
shared_workspace(algorithm, model, geometry)

Return the deterministic, geometry-only part of algorithm's per-run workspace that is safe to build once and share across concurrent runs — for local-update algorithms with a colored proposal scheme, the scheme's visiting_order; nothing otherwise (the default). sweep_Ts builds it once per sweep and hands it back to algorithm_workspace(algorithm, model, geometry, state, shared), so expensive deterministic constructions (DSATUR lattice coloring) run once per sweep instead of once per (temperature, run). Everything mutable — the site cursor, the AcceptanceCache — stays per-run.

source
UnitCellMC.ghost_site — Function
ghost_site(geometry, ghost)

Return the index of ghost site ghost in the cluster algorithms' site-indexed arrays. Ghosts (used to attach external fields to the cluster updates) follow the lattice sites, so ghost ghost lives at index geometry.n_sites + ghost. Clusters attached to a ghost are never flipped (see draw_cluster_flips!).

UnitCellMC.draw_cluster_flips! — Function
draw_cluster_flips!(rng, workspace, geometry)

Draw the per-cluster orientation decisions of a Swendsen-Wang update — one coin flip per cluster root, in the first-encounter order of workspace.roots — recording them per label in workspace.flip, then freeze every ghost-attached cluster by setting its flip entry to false (ghost labels are those of the ghost_site indices), since ghost-attached clusters are never flipped.

Each model's apply_clusters! calls this before mutating the state, so the ghost convention lives in one place; models supply only the per-site mutation.

Returns

workspace.flip.
